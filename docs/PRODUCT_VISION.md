## 1. Haze Flow는 어떤 앱인가?

Haze Flow는 일상의 계획과 실제 행동을 기록하고, 시간이 지난 뒤 자신의 삶을 돌아볼 수 있도록 돕는 개인 생활 관리 앱이다.

이 앱의 출발점은 **What Are You Doing Now?** 였다.

당시의 핵심 경험은 단순했다.

1. 지금 무엇을 하고 있는지 입력한다.
2. 기록한다.
3. 시간과 함께 저장된다.

Haze Flow는 여기에서 출발해 일정, 루틴, 운동, 공부, 식사, 건강, 가계부, 일기, 통계와 회고까지 확장됐다.

하지만 기능이 많아졌다는 이유로 가장 중요한 경험이 복잡해져서는 안 된다.

**Haze Flow의 핵심은 적은 노력으로 자신의 삶을 기록하고, 시간이 흐르며 발견한 변화가 다음 일상을 이어갈 힘이 되도록 돕는 것이다.**

### Haze Flow를 만드는 근본적인 이유

Haze Flow는 기록을 통해 사용자가 **시간에 따른 자신의 변화를 발견하고, 그 변화에서 응원을 얻으며, 일상의 루틴을 통해 삶을 이어갈 힘을 기르도록 돕는 앱**이다.

기록은 단순히 과거의 행동을 저장하거나 생산성을 평가하기 위한 것이 아니다. 과거와 현재를 비교해 자신이 무엇을 해왔고 어떻게 달라졌는지 이해하기 위한 것이다. 운동 능력의 변화, 반복된 작은 행동, 중단 후 다시 시작한 경험도 돌아볼 가치가 있다.

기록이 없거나 계획을 지키지 못한 날을 실패로 판단하지 않는다. 수치가 개선되지 않았다고 무조건 긍정적인 말을 만들지도 않는다. **실제 기록을 근거로 변화와 정체를 정직하게 보여주되, 사용자를 평가하거나 압박하지 않는다.**

Haze Flow의 궁극적인 성공 기준은 기록량, 연속 달성 일수, 생산성 점수가 아니다. **사용자가 자신의 삶을 더 잘 이해하고, 다시 일상으로 돌아와 다음 행동을 이어갈 힘을 얻는가**이다.

이 목적은 활동 기록, 루틴, 통계, 회고 등 모든 기능의 설계 판단에 우선 적용한다. 다만 이 비전만으로 새 기능이나 대규모 UI 변경이 자동 승인되는 것은 아니다. 구현 우선순위와 변경 범위는 프로젝트 가이드 및 공통 작업 지침을 따른다.

## 2. 제품이 해결하려는 문제

사용자는 자신의 생활을 체계적으로 관리하고 싶지만, 기록 자체가 또 하나의 일이 되는 것은 원하지 않는다.

다음 문제를 해결해야 한다.

- 매번 카테고리와 세부 옵션을 선택하는 번거로움
- 같은 내용을 여러 화면에 반복 입력하는 문제
- 운동처럼 반복적인 기록에 지나치게 많은 조작이 필요한 문제
- 데이터는 많이 쌓이지만 실제 변화가 잘 보이지 않는 문제
- 여러 기기에서 기록이 누락되거나 덮어써질 수 있다는 불안
- 기능 추가로 인해 기존의 간단한 사용 흐름이 무너지는 문제

제품의 성공은 기능 개수보다 **일상에서 지속적으로 사용하기 쉬운가**로 판단한다.

## 3. 핵심 설계 원칙

### 3.1. 입력은 단순하게, 분석은 풍부하게

기록하는 순간에는 최대한 적은 조작만 요구한다.

반대로 기록을 돌아보는 화면에서는 날짜별 비교, 추세, 통계, 연관 정보를 충분히 제공한다.

**입력 화면의 단순함과 분석 화면의 풍부함은 서로 모순되지 않는다.**

### 3.2. 한 번 입력한 데이터는 다시 입력하지 않는다

활동 기록이 운동·공부·식사·지출 등 다른 기능과 연결될 수 있다면 기존 기록을 재사용한다.

단, 자동 연결 과정에서 중복 기록이나 중복 집계가 발생해서는 안 된다.

### 3.3. 자동화하되 사용자의 선택을 존중한다

규칙으로 추론할 수 있는 정보는 자동으로 처리한다.

사용자가 직접 수정한 값은 자동 추론보다 우선한다.

불확실한 값은 억지로 추정하지 않는다.

### 3.4. 기존 기록을 최우선으로 보호한다

UI 개선을 위해 기존 데이터 구조를 무리하게 변경하지 않는다.

활동 시간, 사진, 운동 세트, 연결된 지출, 계정별 데이터, 동기화 상태가 유지되어야 한다.

기존 기록이 손실될 가능성이 있다면 기능 추가보다 데이터 보존을 우선한다.

### 3.5. 사용자의 생활에 제품이 맞춘다

사용자가 생활의 불편함을 설명했을 때 입력 방식·화면 구성·타이머 조작법을 전부 스스로 설계하도록 요구하지 않는다. AI 작업자는 실제 사용 순서와 반복 조작을 분석해 **가장 적은 입력과 재입력으로 해결하는 기본안**을 먼저 제안한다. 사용자가 이미 말한 맥락은 되묻지 않는다.

관찰된 불편, 설계 가설, 승인된 UX, 구현·실기기 검증을 구분한다. 자동화가 추측이나 데이터 손실을 정당화하지 않는다. 큰 변경은 기존 작업 경계에 따라 별도 결정한다.

### 3.6. 모든 기능을 매일 사용하도록 강요하지 않는다

일상 기록만 남기는 날도 있고, 운동이나 공부를 자세히 기록하는 날도 있다.

사용자가 입력하지 않은 값을 결측이나 실패로 취급하지 않는다.

필요한 기능만 사용할 수 있어야 한다.

### 3.7. 기록할 때는 가볍게, 돌아볼 때는 깊게

입력 순간의 조작은 최소로 두고, 돌아보기·비교·회고에서는 당시의 생활과 변화를 충분히 발견할 수 있게 한다. 빈 날을 실패로 평가하거나 매일 기록을 강요하지 않는다. 이 원칙은 3.1과 같은 방향이며, **시간이 쌓일수록 기록이 더 소중해지는 경험**을 제품의 성공 기준으로 삼는다.

### 3.8. 한 번 기록하고 목적에 맞는 여러 모습으로 본다

같은 원본을 중복 입력하지 않고, 캘린더·목록·보드·차트·회고 등 **목적에 맞는 뷰**로 보여 주는 것을 지향한다. Notion의 다중 뷰·즉시 반영 경험에서 배운 점이며, Notion 복제가 목표가 아니다. Haze Flow에 필요한 범위만 선택적으로 적용한다. 드래그 앤 드롭·보드 전면 도입은 별도 승인 전까지 자동 착수하지 않는다.

### 3.9. 데이터는 사용자의 자산이다

특정 서비스에 기록이 갇히지 않아야 한다. JSON 백업·복원, 구조화 데이터의 CSV 등 실용적 내보내기, 일기·회고의 Markdown 활용, 사진 원본과 기록의 연결 보존을 중시한다. Obsidian에서 배운 **소유와 이식성**의 가치이며, 모든 저장을 Markdown으로 바꾸라는 뜻이 아니다. 복잡한 플러그인·설정 없이 바로 쓸 수 있는 기본 화면을 유지한다.

### 3.10. 제품 설계 원칙 여섯 가지 (2026-11-09 확정)

1. **한 번 기록하고 다양하게 활용한다.**
2. **조작은 직관적이어야 한다.** 상태 변경·수정·탐색은 가능한 한 단순하다.
3. **사용자가 설정 전문가가 될 필요는 없다.** 유용한 기본 화면을 두고, 커스터마이징은 필요할 때만 선택한다.
4. **데이터는 사용자의 자산이다.** 백업·내보내기·향후 다른 앱과의 호환을 고려한다.
5. **기록은 시간이 지날수록 가치가 커져야 한다.** 통계뿐 아니라 당시의 생활과 변화를 발견할 수 있어야 한다.
6. **보기 좋은 디자인과 사용성을 함께 추구한다.** 기능이 많다는 이유만으로 좋은 앱이라고 보지 않는다.

원하지 않는 결과물: 기능만 잔뜩 넣은 복잡한 앱. 원하는 결과물: **오래 쓸수록 더 좋아지는 나만의 생활 관리 앱.**

### 3.11. 전체 UI 시각 방향

전체 Haze Flow는 **현대적이고 세련된 라이프·생산성 대시보드**를 기준으로 한다. 밝고 산뜻한 색, 부드러운 포인트, 읽기 쉬운 타이포, 충분한 여백, 명확한 정보 위계, 보기 좋은 데이터 시각화를 지향한다. 같은 카드의 기계적 반복과 과도한 화면 복잡성은 피한다.

적용하지 않을 전체 UI 톤: 레트로, 타자기, 종이 질감, 구식 프로그램, 잡지 마스트헤드로 앱 전체를 만드는 것.

**AI 사진 일기(사진+글을 포토 에세이처럼 조판)** 는 별도 향후 기능의 표현이며, 그 스타일을 앱 전체에 적용하라는 뜻이 아니다. 상세·시안 상태는 [UI_DESIGN_DIRECTIONS.md](UI_DESIGN_DIRECTIONS.md).

## 4. 최우선 UX — 활동 기록

### 4.1. 목표 경험

사용자는 앱을 열고 곧바로 다음 질문을 마주한다.

**"지금 뭐 하고 있어?"**

기본 입력 영역에는 다음 요소를 우선 배치한다.

- 한 줄 기록 입력창
- 활동 시작 / 짧은 기록 선택
- 기록 버튼

카테고리, 사진, 기록 시간 변경 등은 필요할 때 펼치는 추가 설정으로 이동한다.

화면이 단순해지더라도 기존 기능을 삭제해서는 안 된다.

### 4.2. 활동 시작과 짧은 기록

**활동 시작**은 일정 시간 지속되는 행동을 기록한다.

예: 영어 공부 시작, 운동 시작, 책 읽기.

기존 활동 시작·종료 및 시간 계산 규칙을 유지한다.

**짧은 기록**은 특정 순간의 사실이나 메모를 남긴다.

예: 점심으로 김치찌개 먹음, 오늘 기분이 좋음.

두 방식은 사용자가 쉽게 구분하고 선택할 수 있어야 한다.

### 4.3. 자동 카테고리 분류

입력한 문장을 규칙 기반으로 분류한다.

| 입력 예시 | 예상 분류 |
|---|---|
| 레그프레스 25 10 | 운동 |
| 영어 공부 시작 | 공부 |
| 점심으로 김치찌개 먹음 | 식사 |
| 회의 참석 | 업무 |
| 분류가 불확실한 문장 | 일상 |

구현 원칙:

- 기존 운동 파서와 충돌하지 않는다.
- 외부 유료 AI API를 사용하지 않는다.
- 자동 분류 결과는 사용자가 수정할 수 있다.
- 사용자의 수동 선택이 자동 분류보다 우선한다.
- 입력 원문을 보존한다.
- 확신할 수 없는 경우 무리하게 세부 카테고리를 추정하지 않는다.

## 5. 운동 기록 UX

운동 기록은 일상 기록보다 세부 정보가 필요하지만, 입력 과정은 간단해야 한다.

### 5.1. 입력 규칙

- 중량 운동: 운동명 / kg / 횟수 / 세트
- 러닝머신: 운동명 / 속도 / 시간(분)
- 천국의계단: 운동명 / 속도 또는 레벨 / 시간(분)
- 마이마운틴: 운동명 / 각도 / 속도 / 시간(분)

예시:

`레그프레스 25 10 3`

`러닝머신 3.5 2`

**일반 러닝머신에는 경사 입력을 요구하지 않는다.** 0kg 운동 기록도 유효하다.

### 5.2. 향후 개선 방향

- 한 운동 안에서 여러 기구와 세트를 관리한다.
- 같은 기구의 세트를 묶어서 표시한다.
- 세트별 중량과 횟수를 다르게 기록할 수 있다.
- 이전 운동 기록을 쉽게 참고하거나 복사한다.
- 예상 사용 근육과 실제 자극을 느낀 근육을 구분한다.
- 운동 중에는 입력 속도를 우선하고, 상세 분석은 나중에 확인한다.

운동 중 실제 사용 흐름, 운동별 독립 상태, 세트별/일괄 기록, 휴식 경과 측정의 구체적 합의는 [운동 UX 기준](WORKOUT_UX.md)을 따른다. 활동 입력 간소화 및 데이터 보존과의 충돌을 먼저 점검하고 작은 단위로 구현한다.

## 6. 기능별 제품 원칙

### 일정과 루틴

계획과 실제 수행 기록은 구분한다.

반복 루틴은 한 번 설정한 뒤 날짜별 실행 여부를 관리한다. 루틴 수정이 과거 실행 기록을 변경해서는 안 된다.

### 공부

공부 시간뿐 아니라 결과, 다음 행동, 복습할 질문을 연결한다.

Obsidian이나 블로그로 이어지는 기능은 중복 작성을 줄이는 방향으로 설계한다.

### 식사와 건강

기록된 식사, 운동, 신체 수치를 비교해 변화를 확인한다.

자료가 부족하면 부족하다고 표시한다. 추정 칼로리나 회복 상태를 측정된 사실처럼 표현하지 않는다.

### 가계부와 쇼핑

**은행·카드사·현금영수증의 결제·환불 증빙을 먼저 수집·대조해 소비 원장을 구성한다.** 카드 승인·매입, 계좌 출금, 카드대금 납부, 현금영수증 등 동일 소비의 복수 증빙을 중복 집계하지 않는다.

그다음 네이버·쿠팡·지그재그·11번가·G마켓 등의 주문·상품 정보를 결제에 연결한다. 연결되지 않은 결제는 사용자에게 구매처를 확인받고, 필요한 추가 쇼핑몰 자료만 수집한다. 금액·날짜 일치만으로 연결을 확정하지 않는다.

주문 총액, 상품 금액, 할인, 배송비, 포인트, 복합결제, 부분 취소·환불을 구분한다. 결제와 주문은 일대일 관계라고 가정하지 않는다. 상품 정보가 없는 결제도 원장에 남기되 품목별 단가·구매 간격 분석에는 임의 배분하지 않는다.

이것은 **향후 설계 방향**이며 현재 쇼핑몰 파일 가져오기 기능이 결제 중심 수집을 구현했다는 뜻이 아니다. 기존 기록·수동 수정·연결을 보존하며 단계적으로 전환한다. 상세 기준은 [결제 원장 설계](payment-ledger-plan.md)를 따른다.

### 일기와 회고

기존 활동 기록을 활용해 하루를 돌아볼 수 있어야 한다.

기록이 없는 시간의 행동이나 감정을 임의로 만들어 내지 않는다.

과거 비교·주간 회고·인바디·운동 변화처럼 **시간이 쌓인 기록을 다시 펼치는 즐거움**을 우선한다. 숫자 대시보드만으로 돌아보기를 대체하지 않는다.

### 통계와 분석

사용자가 자신의 변화를 직관적으로 이해할 수 있도록 차트를 활용한다.

수치의 단위, 비교 기간, 누락된 데이터, 추정 여부를 명확하게 표시한다.

## 7. 기술 및 데이터 보존 원칙

현재 웹앱과 저장소 구조를 유지한다. **당장 저장 형식을 Markdown 전용으로 바꾸거나 스키마를 전면 교체하지 않는다.**

- Vite 기반 웹앱과 GitHub Pages 배포
- IndexedDB 기반 로컬 기록 저장
- Supabase 계정 및 기기 간 동기화
- 계정별 데이터 분리
- JSON 백업 및 복원
- 기존 기록·사진·통계와의 호환성
- 가계부 등 구조화 데이터의 CSV 내보내기·가져오기(해당 기능 범위)
- 일기·공부 등 문장형 기록의 Markdown/문서 내보내기 경로(있는 범위에서 유지·보완)
- 사진 참조와 기록 간 연결이 백업·동기화에서 끊기지 않을 것

IndexedDB와 Supabase는 서로 대체 관계가 아니다.

새 UI가 저장·수정·삭제·동기화의 기존 동작을 훼손해서는 안 된다.

저장 성공 여부를 실제로 확인하기 전에는 성공 메시지를 표시하지 않는다.

데이터 소유감의 목표는 **특정 확장자가 아니라, 기록을 계속 백업·이전·재활용할 수 있다는 확신**이다.

## 8. 개발 우선순위

### 1순위 — 데이터 보존과 치명적 오류

기존 기록 손실, 동기화 충돌, 저장 실패, 사진 누락 등 실제 사용을 방해하는 문제를 우선 해결한다.

### 2순위 — 매일 사용하는 화면의 편의성

한 줄 활동 기록 UX를 완성하고 운동 기록 과정을 개선한다.

### 3순위 — 기존 기능 완성도

실제 사용 과정에서 발견된 불편, 잘림, 입력 오류, 분석의 불명확성을 개선한다.

### 4순위 — 추가 자동화와 외부 연동

결제 원장 중심 데이터 수집·연결의 상세 기준은 [결제 원장 설계](payment-ledger-plan.md)를 따르고, 진행 우선순위는 [프로젝트 가이드](PROJECT_GUIDE.md)에서 관리한다. 은행·카드 **자동** 연동 가능 여부는 확인 전까지 보장하지 않는다. 새로운 AI 기능·새 앱 플랫폼은 기존 핵심 경험이 안정된 후 검토한다.

**새 기능을 추가하는 것보다 이미 있는 기능을 편하게 사용하는 것이 우선이다.**

## 9. 개발 완료 판단 기준

Haze Flow가 완성됐다고 판단하기 위해 모든 아이디어가 구현될 필요는 없다.

다음 조건을 우선 충족해야 한다.

1. 일상 기록을 빠르고 부담 없이 남길 수 있다.
2. 운동과 공부 등 자주 쓰는 기능을 불편 없이 사용할 수 있다.
3. 기록의 저장·수정·삭제가 안정적으로 작동한다.
4. iPhone과 Mac 등 기기 간 동기화가 실제로 검증됐다.
5. 기존 데이터와 사진을 안전하게 보존하고 복원할 수 있다.
6. 통계와 회고에서 기록한 변화와 다시 시작한 경험을 사실에 근거해 확인할 수 있다. 기록이 없거나 성과가 낮은 날을 실패로 낙인찍지 않는다.
7. 알려진 중대한 오류가 해결됐고, 남은 제약은 문서화됐다.

추가 기능에 끝이 없다는 이유로 출시와 실사용을 계속 미루지 않는다.

## 10. 가장 중요한 판단 기준

새 기능이나 디자인 변경을 제안할 때마다 다음 질문을 적용한다.

**"이 변경으로 사용자가 자신의 삶을 더 쉽게 기록하고, 실제 변화를 이해하며, 다음 일상을 이어갈 힘을 얻을 수 있는가?"**

그렇지 않다면 우선순위를 낮춘다.

Haze Flow는 사용자가 앱을 관리하기 위해 사는 것이 아니라, **자신의 삶을 살아가면서 자연스럽게 기록을 남기기 위한 도구**다.
